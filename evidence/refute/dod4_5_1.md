# Refuter report dod4_5_1 (DoD 4 and DoD 5)

Date 2026-10-10. Read-only on source. Ports 8774/8775 only; every server was killed with `taskkill /F /T` (no listeners or hiveshot python processes remain). Raw outputs: `evidence/refute/dod4_5_1/*.txt|json`. Harness scripts were in the session scratchpad (h.py, dod4.py, crafted.py, align.py, dod5a-d.py, csvt.py).

## DoD 4: "Every recorded shot can be opened in the 3D viewer and replayed with field, HIVE, robot and ball path." -> NOT REFUTED (data contract level; no browser, so WebGL rendering itself is unverified)

What the viewer needs (ui/viewer3d.js, ui/app.js):
- `/api/shots/{id}`: `track[{t,x,y,z}]`, `launch_point`, `parabola{a,b,c,rmse_in}`, `ball_type`, `result`, `equation`, `exit_*`, `launch_*`, `apex_z_in`, `drag`, `clip_url`.
- `/api/field/geometry`: `wireframe[[a,b]...]`, `hives.{red,blue}.cells.{audience,far}.{opening[],is_up}`, `bounds`.
- `/api/config`: `robot.{length,width,height,launch_exit_height}`.
- Static: `/`, `styles.css`, `app.js`, `viewer3d.js`, `vendor/three.module.min.js`, `vendor/OrbitControls.js`.

Results (dod4_contract.txt):
- synth_basic (6 shots) and synth_burst (6 shots), run to completion in a fresh data dir: for EVERY shot the track has 51-75 points, all finite, strictly increasing t; parabola a/b/c/rmse finite (rmse 0.07-0.16 in); launch_point finite and inside bounds (min -72,-72,0 / max 72,72,120); azimuth, angle, apex, exit speed finite; equation non-empty; ball_type pollen, result in the allowed set. No problems flagged.
- Geometry in both tip states (red audience-up and red far-up): 30 wireframe segments, 4 cells each with finite opening polygon of >=3 vertices, `is_up` bool correct and it changes with the state. Robot dims all finite.
- Viewer formula check (dod4_alignment.txt): evaluating `par.a*s^2+par.b*s+par.c` with s = horizontal distance from launch_point (exactly as viewer3d.js does) differs from track z by at most 0.21-0.74 in for all 6 basic shots, and the viewer's first-to-last track direction matches the API `launch_azimuth_deg`. The dashed ghost overlays the measured path.
- Static: every src/href in index.html, the importmap target, and the relative JS imports return 200 with correct MIME (JS served as text/javascript, needed for ES modules). Every identifier the viewer and OrbitControls import from three (45 names) is exported by the vendored three r170 build.
- Pipeline invariant: `_finalize` drops tracks with fewer than 4 points before storing, so every stored real shot has a replayable track.
- Adversarial/crafted shots written through Store (dod4_crafted.txt), including session "unassigned": result=UNKNOWN with track/parabola/launch_point/speeds all None, empty-points track, 1-point track, ball_type unknown, duplicate-t track. API returns 200 with `track: []` or short track and null parabola/launch_point; the JS guards all of these (`(shot&&shot.track)||[]` returns early, `if (par)`, `shot.launch_point || first point`, `fmt()` handles null, `shot.equation || ... || ''`). The "unassigned" session lists, shows stats, tips and exports normally and its shots open via /api/shots/{id}.

Weaknesses (do not refute the claim):
1. A parabola containing NaN (crafted; not producible by the pipeline since recon filters non-finite points) makes `GET /api/shots/{id}` return 422 "Out of range float values are not JSON compliant", so that shot cannot be opened (the UI would toast the error). No sanitising in `shot_full`/`add_shot`.
2. Shots tab filter has no `unknown` option; UNKNOWN shots appear only under "all".
3. An UNKNOWN shot with empty track opens the Replay tab but shows an empty scene (no robot, no path), and the info panel is rendered; there is no explicit "no track" message.
4. Robot box is centred on the launch point (the exit mark is in the middle of the box), a visual approximation, not a measured robot pose.
5. Actual WebGL rendering, playback and scrub were not exercised (no browser permitted). Browser evidence is evidence/m4_e2e/browser_pass_1.txt, which I did not re-verify.

## DoD 5: "Data persists across an application restart. Sessions export to CSV." -> NOT REFUTED

Persistence (dod5a_restart.txt, dod5b_killmid.txt, dod5c_diff.txt, dod5d_continue_and_randkill.txt):
- synth_basic run to completion with a manual HIVE flip (2 tips), then `taskkill /F /T` (the .db was 4 KB and all 6 shots sat in the 449 KB -wal, i.e. an ungraceful kill with an un-checkpointed WAL). `PRAGMA integrity_check` = ok, 6 shots. Restart on the same data dir: sessions, all 6 full shot records (track, parabola, drag, launch_point), tips, stats and CSV were byte-for-byte identical to the pre-kill dump (dod5a_dump.json). All 6 clip files exist, 92-138 KB.
- Starting again on the same data dir with autostart: new session with 6 shots, first session's shots unchanged, shot ids 1-12 unique and continuing (AUTOINCREMENT).
- Mid-pipeline kills, 7 trials (realtime and lockstep, kill after the 1st/2nd/3rd shot, random time): integrity_check ok every time; every shot observed through the API before the kill was present after restart (missing=[]); shots stored just before the kill were also present (db had more than observed in 4 trials). Only difference between pre-kill and post-restart records: `clip_url` set after the shot was announced (clip written after the shot row), expected.
- 8 further random-time kills (0.2-4 s) on synth_burst: integrity ok, nothing lost, every stored shot fetchable via the API after restart.
- Copy of the data dir (db+wal+shm) taken while the app ran: integrity ok, 2 shots, served correctly by a second app instance.

CSV (dod5_csv.txt): crafted session with a UNKNOWN shot (all None), nectar/bounce_out shot, note containing comma, quotes, newline and non-ASCII, extreme magnitudes, plus "unassigned" and an empty session:
- Header equals `stats.CSV_FIELDS` (16 columns; docs/api.md only says "stats.shots_to_csv"). Parses with `csv` module; every row has 16 columns; data rows == shots in the API for all three sessions, including empty (header only) and "unassigned". 404 for unknown session.
- Values equal the API's within 1e-9 relative (t_launch, exit speed, angle, apex, parabola_a); None -> blank; exit_speed_mps = ips*0.0254; quoting of the multi-line/comma/quote note round-trips. Content-Type text/csv, Content-Disposition attachment `session_<id>.csv`. The real run CSV (6 rows) has parseable numerics.

Weaknesses (do not refute):
1. Sessions are never closed by a crash or a normal app exit, so after restart the old session still has `ended_at: null` (shows "(running)" in the picker; two "running" sessions accumulate after a second run). Data is intact; only labelling.
2. CSV is LF-terminated and has no BOM (server reads the temp file with `read_text`, which drops the CRLF `csv` wrote); valid for Python/most tools; Excel may mis-decode non-ASCII notes (notes are ASCII in practice).
3. `notes` starting with `=` is not neutralised (CSV formula injection); notes are system generated, so low risk.
4. `t_launch` is camera-clock seconds (0.0 in fixtures), not wall-clock; the CSV has no absolute timestamp, no drag-fit or launch_point columns.
5. A NaN in a stored parabola would be written as `nan` in the CSV (still parseable by float()).
6. Not tested: power loss/OS crash (only process kill), the packaged build, or a live RTMP/capture source.
