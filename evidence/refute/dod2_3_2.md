## Attack 5: breaking the real-time path

- Two MJPEG clients plus `/stats` at about 10 Hz: 20-shot fixtures stay 20/20 (8 of 8 runs, 3 on the snapshot; drops 0-17 per camera, warned whenever non-zero). The streams delivered data (1.4-4.2 MB each) and no `/stats` call failed. `/stats` latency under contention reached 75 ms on a quiet machine but **1.5-3.2 s** at 60 fps/240 fps when the machine was at 50-60 % (preview encode averages 1.3 s per frame in status.timing.preview_ms in the worst run).
- 240 fps with the same clients (10 snapshot runs): 8/8 in 7; **7/8 in 2 runs (s8_240_99, 96 and 115 dropped frames per camera) and 2/8 in 1 run (s8_240_7)**. The two 7/8 runs raised "camera ... dropped N frames (processing too slow)" and "3 ball track(s) could not be paired" warnings, so they are flagged. The 2/8 run is **silent**: both cameras read all 782 frames, dropped 0, status.warnings empty, no ERROR in the server log, only shots 1 and 2 stored (see below). Whole-machine CPU was 58 % mean (foreign load included).
- Dropped frames never produced a wrong label on a recorded shot; they cost shots and add a few percent of speed error (4.60 % at 240 fps with 125 dropped frames per camera, vs 1.3 % otherwise).

### Silent shot loss (the weakness that matters)
1. `dod2_3_2/s20_2718_rt.*` (run at about 20:18 on the working tree, realtime, no clients, other agents' servers running): **2/20 shots stored**, shots 3-20 missing, cams read all 1008 frames, dropped 0, warnings empty, no ERROR in the log, only the line "time offset ... 0.0000 s (confidence 0.87)". Nine identical re-runs of the same fixture and mode (idle-waited or not, with and without clients) gave 20/20. Not reproduced.
2. `p2/s8_240_7_rt_s1.*`: 2/8 stored with the same silent signature. Five identical re-runs (s2..s6) gave 8/8.
3. Controlled saturation (`dod2_3_2/p2load/`, 12 busy-loop processes on the 16 logical cores, my own load): 5 of 5 runs record **0/20**. In 3 of 5 the failure is at least visible: `status.warnings` contains "cam1: Unknown C++ exception from OpenCV code" (and, in realtime, "dropped 989 frames"), and the server log shows `camera loop failed for cam0/cam1` from `cv2.resize(..., dst=buf, interpolation=INTER_AREA)` in `ScaledDetector.shrink` (pipeline.py line 418 in the Phase 2 snapshot): both camera threads die within about 2 s. Two runs are silent (lockstep `p2load/s20_2718_lockstep_load12_904372655.*` on the snapshot, and realtime `s20_2718_rt_x_load12.*` on the working tree): 1008 frames read, 0 shots, no warning, no ERROR line (the lockstep one has no "time offset" line either, so no 2D track ever reached the reconstruction). One lockstep run hung for 300 s with the cameras stuck at 6 frames. The same exception kills the camera loops in an in-process `Pipeline` run (evidence/refute/dod2_3_2/inproc/). A run with 4 burners (66 % mean CPU) was 20/20.
I did not find the root cause of the moderate-load silent losses (1 and 2). They are non-deterministic and appeared only when the machine was shared; I cannot show they occur on an idle PC, and I cannot show they cannot. Candidate area: a failure that kills or starves the 2D detection/track path without setting an error, since no recon-stage warning ("found no partner", "could not be paired") was raised.

## Weaknesses (regardless of verdict)
- Synthetic only, truth calibration, noise-free, circular truth flag, simulator speed as reference (see top). "At least 95 % detection" is easy on a flat grey background with a solid ball; 0.97-1.00 recall says nothing about real footage.
- Fast low-arc shots (44-48 deg, 490-580 in/s) are classified `unknown` when the ball reaches the CELL fast; `unknown` counts as a failure in the histogram and the make rate (so a perfect run reads 0.50 and puts three false failures in the histogram). 350-375 in/s shots at the same angle were fine. Typical fixture speed in the docs is 230 in/s, so this is outside the nominal envelope, but the operator would see wrong statistics with no warning.
- Silent shot loss under CPU contention (above): the status/warnings channel does not cover every loss path, and a dead camera loop (OpenCV exception) is visible only as a warning string, with the pipeline staying "running".
- Warning noise: "N ball track(s) could not be paired ... shots may be missing" appears on healthy 240 fps and 0.15 s-overlap runs where every shot was recorded correctly, which trains the operator to ignore it. A transient "connected but no frames received yet" appears at every realtime start.
- 240 fps realtime is only fully dependable with CPU headroom: with 2 preview clients and a shared PC it dropped 11-129 frames per camera and lost shots in 3 of 10 snapshot runs; accuracy of the shots that survive is unaffected apart from the 4.6 % case.
- Failure-order histogram buckets index 6 and above into "5" (burst6 fixture). Consistent with docs, but the histogram cannot tell 5 from 6.
- Exactly 1.5 s between shots is a coin flip at 60 fps (frame quantisation), as in round 1 (not retested).
- Sample size: three 20-shot seeds, three 240 fps seeds, five adversarial fixtures; shots per fixture are small (6-9 for adversarial).
- Mid-run source edits by the lead: results before and after 21:40 are not on identical code; the snapshot set (`p2/`) is the clean one.
